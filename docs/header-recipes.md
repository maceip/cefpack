# The facts that were expensive to learn

Everything here cost a build, a fetch or a crash to find out.  It is
written down so that the next person does not have to.

## The C API is versioned, and the version is the contract

The public headers of the engine carry the version of the C API:

```c
#define CEF_API_VERSION_LAST CEF_API_VERSION_15600
```

The generated declarations carry it too, in a slightly different form:

```rust
pub const CEF_API_VERSION_LAST: i32 = 15600;
```

Two engines of the **same API version** have the same C API, on every
platform: the platform decides which libc the types come from, and the
widths of those types are the same on every 64 bit target.  Two engines of
**different** API versions do not, and the difference is not a compile
error — it is a program that writes into the wrong place.

Therefore: **compare the two, and refuse to build when they differ.**  That
check is the whole fix for the bug that this project started with, where the
declarations of a desktop distribution were reused for Android with no check
at all.

Note the two forms of the constant.  The headers write
`CEF_API_VERSION_15600`, the bindings write `15600`; a parser that expects
one form and finds the other will report that the bindings "do not name the
API version", which is true and useless.

## The C API headers are generated, not checked in

Of the 161 headers under `include/capi/`, exactly one is in the source
tree: `cef_base_capi.h`.  The other 160 are written by

```bash
python3 tools/version_manager.py <cef_dir>
```

which needs `<chromium>/chrome/VERSION` to know which Chromium the headers
describe (`MAJOR=156 / MINOR=0 / BUILD=8078 / PATCH=96` for the pinned
commit).  A tree that only has CEF checked out cannot generate them.

## Four more headers come out of the build

| header | written by | needs |
|---|---|---|
| `cef_config.h` | `tools/make_config_header.py <out.h> <args.gn>` | the arguments of the build |
| `cef_version.h` | `tools/make_version_header.py <out.h>` | the version of CEF |
| `cef_api_versions.h` | `tools/make_api_versions_header.py` | `cef_api_versions.json` |
| `cef_color_ids.h` | `tools/make_colorids_header.py` | three headers of Chromium |
| `cef_command_ids.h` | `tools/make_pack_header.py` | one header of Chromium |

And two more that only a real Chromium build can produce, because they are
generated by **grit**, the resource compiler of Chromium:

- `cef_pack_resources.h`
- `cef_pack_strings.h`

This is why the generator of the declarations of Rust needs a built
Chromium, and why the fallback of `cefpack bindgen` exists.

## The Chromium revision is the *position* of the CEF commit

CEF does not name a Chromium commit.  It names a **position** on the
Chromium branch: the N-th commit of the branch that Chromium had when CEF
was rebased onto it.  In the Chromium repository:

```bash
git log -2 <cef-commit>              # gives refs/heads/main@{#N}
git log -1 --grep='refs/heads/main@{#N}' origin/main
```

gives the Chromium commit.  `tools/automate/automate-git.py` does exactly
this, and `gclient` reads the result from CEF's `DEPS` file — which is why
the pin of this repository can be a single commit of CEF and the Chromium
side still cannot drift away from it.

## One header of Chromium at a time

A single file of Chromium can be fetched at a pinned ref:

```text
https://raw.githubusercontent.com/chromium/chromium/<chromium-version>/<path>
```

The plain version branch works; `refs/branch-heads/...` does not.  This is
how the headers that the public headers of CEF include are fetched, each
one checked against a SHA-256 in the manifest.

## The branch names of CEF are four digits

The release branches of CEF are the numbers of CEF — `156`, `1650`, `2743`
— and **not** the numbers of Chromium.  The master branch is `master`.

## The repository of CEF

`https://github.com/chromiumembedded/cef`.  The pinned commit of CEF
156.0.30 is `6028375a4532fb89d23b58635f5c0d3a82c93959`, on the branch
`156`, tracking Chromium 156.0.8078.96.

## The size of the checkout

The Chromium checkout is tens of gigabytes, and about a hundred with the
history.  A build of the engine takes hours.  Both are reasons why the
build has its own machine and its own cache, and why the sources are
cached between the runs.

## The NDK is a complete C++ toolchain

The NDK r27c (27.2.12479018) is clang 18, lld, bionic and libc++ — a
complete C++ toolchain for Android.  `cc-rs` does **not** find the NDK
compiler from `ANDROID_NDK_HOME` alone; the compiler has to be named:

```bash
export CC_aarch64_linux_android=aarch64-linux-android29-clang
export CXX_aarch64_linux_android=aarch64-linux-android29-clang++
export AR_aarch64_linux_android=llvm-ar
export CARGO_TARGET_AARCH64_LINUX_ANDROID_LINKER=aarch64-linux-android29-clang
export PATH="$PATH:<ndk>/toolchains/llvm/prebuilt/linux-x86_64/bin"
```

## A note for the sandboxes

When the workspace of a session lives on a network mount, `rustc` can fail
with "failed to map object file: memory map must have a non-zero length".
The work-around is to put the target directory on a local disk and to turn
the incremental compilation off:

```bash
export CARGO_INCREMENTAL=0
export CARGO_TARGET_DIR=/root/cefpack-target
```
