# The embedding: the part that is still missing

This is the part of the work that a build of the engine does **not** solve,
and it is the reason that "just build CEF for Android" is not the whole
story.  It is written down here so that nobody has to rediscover it.

## What upstream CEF gives, and what it does not

CEF is Chromium packaged as a library.  On the desktop, the library is
linked into an application that owns the process, the message loop and the
window system.

On Android, an application is a sandboxed process that the system starts,
that has no window system and that must answer to a lifecycle.  Chromium on
Android is not a library: it is Chromium **plus** an embedding — a Java
layer, a content delegate, the child processes and the way the resources are
read out of the package.

Upstream CEF has none of that:

- there is **no `android/` directory** in the tree — not in `master`, not in
  the newest release branches (checked against `2743`, `2704`, `2454`);
- exactly **one** path of `master` contains the word "android", and it is
  `tools/yapf/platformdirs/android.py`, a Python formatter's file;
- only **five** files under `libcef/` mention Android at all, and only as
  `#if BUILDFLAG(IS_ANDROID)` guards around POSIX signal handling;
- `tools/automate/automate-git.py` accepts only `windows`, `mac` and `linux`;
- the index of the published distributions
  (`https://cef-builds.spotifycdn.com/index.json`) has no `android` key.

So **"no Android target" means "no prebuilt package", not "cannot compile for
Android"**.  CEF's `include/base/cef_build.h` defines `OS_ANDROID`, and
Chromium's GN and Ninja support `target_os="android"`.  The engine itself
compiles.

What does not exist is the embedding around it.

## What the embedding is

For a CEF application on Android, the following have to exist and have to
work together:

| piece | what it does |
|---|---|
| the Java layer | `org.chromium.base.*` — the glue between the Java virtual machine and the native code; the classes that `libcef.so` finds with `FindClass` at start-up |
| the child processes | the renderer, the GPU and the utility processes, each of them started as a service of the application, each of them loading the same engine |
| the content delegate | the object that tells Chromium how to run inside a process that Android owns |
| the resource loading | the pak files and the locales, read out of the package of the application rather than out of a directory next to the binary |
| the process start-up | the order in which the library is loaded, the command line is parsed and the message loop is entered — the order is not free, and getting it wrong aborts the process |

The third-party port that this project used before is exactly this
embedding, and it is roughly ten thousand lines of it.

## The failure this caused, and the rule that came out of it

The application that shipped with only `libcef.so` in the APK crashed on
launch, every time.  The reason was visible in the package and was not
guessed at:

- `libcef.so` alone references **475** distinct `org/chromium/...` classes
  and exports **3 554** `Java_*` symbols;
- the dex files of that APK contained **zero** classes of `org/chromium/`;
- and `System.loadLibrary` appeared **nowhere** in the history of the
  repository, so the native library was never in the process at all.

A unit test that passes while the application crashes on launch is worse
than no test: it buys false confidence.  The rule that came out of it is
written into the pipeline of this repository and of the application that
consumes it:

> **Nothing is built, published or promised until it has been seen running
> on a device or an emulator.**

That is what `emulator-gate.sh` does for the consumer, and what this
repository's own build job has to earn the right to claim anything about
the engine.

## What has to be written

In the order in which the work bites:

1. **The Java layer.**  The classes that the engine looks up when it starts.
   They are generated by the Chromium build (`base_java`, `chrome_java`) and
   have to be packaged into the APK — and the dex has to be checked, because
   a class that is missing is a crash at start-up and nothing else.
2. **The child processes.**  Android starts a process for a service, and
   Chromium needs its renderer, its GPU and its utility processes to be
   started the same way, each of them with the same engine.
3. **The content delegate.**  The object that binds Chromium to the process
   that Android owns.
4. **The resource loading.**  The pak files and the locales are read out of
   the package.  `ui::SetLocalePaksStoredInApk(true)` and the loader of
   Chromium's own resources decide this, and the order matters: the engine
   has to be loaded by Chromium's loader, so that its `JNI_OnLoad` runs, so
   that the native initialisation hook runs, so that the resources are
   found.  Loading the engine as a plain dependency of the application
   library means that the hook never runs, and the engine aborts looking for
   files that are right there.
5. **The start-up order.**  The command line has to be parsed before the
   engine is initialised, the engine has to be initialised before the
   browser is created, and the message loop has to run on the thread that
   Android owns.

## The honest summary

Building the engine is the part this repository does.  The embedding is a
separate piece of work, of the same order of magnitude as the engine build,
and it is **not** in this repository.  A consumer that wants a browser on
Android needs both, and until the embedding is written, the engine on its
own is a library without a host.
